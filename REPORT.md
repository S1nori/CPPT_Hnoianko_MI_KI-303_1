# Звіт до лабораторної роботи № 1

## 1. Тема, номер і варіант
* **Тема:** Розгортання Java-проєкту та базова обробка даних.
* **Номер роботи та варіант:** Лабораторна робота № 1, варіант № 6 («Реєстр студентів»).
* **Виконавець:** Гноянко М. І., група КІ-303.
* **Операційна система:** Windows 11 (локальна розробка) + Ubuntu, Windows, macOS (перевірка в GitHub Actions).

## 2. Мета роботи
Пройти повний цикл розробки кросплатформного консольного Java-проєкту: від налаштування репозиторію, системи збирання Maven, модульних тестів JUnit 5, статичного аналізатора SpotBugs і пакування виконуваного JAR до автоматичної перевірки на трьох операційних системах у GitHub Actions, публікації артефактів та версіонування релізу.

## 3. Постановка задачі
Розробити консольну утиліту, що зчитує записи про студентів із файлу `data/input.csv` (або шляху, переданого через `--input`) у кодуванні `UTF-8` із роздільником `;`:
`group:String; name:String; average:double; course:int; scholarship:boolean`.

Програма повинна валідувати кожен рядок (фіксуючи номер рядка та причину пропуску для хибних записів без аварійного завершення), обчислювати чотири показники:
1. Кількість коректних записів;
2. Середній бал;
3. Найбільший бал;
4. Кількість стипендіатів.

Результат виводиться в консоль і зберігається у файл (за замовчуванням `out/report.txt` або через `--output`) із фіксованим форматуванням чисел через крапку (`Locale.ROOT`). Також підтримуються прапорці `--help` та `--version` (`<version>+<build>`).

## 4. Структура програми
* `src/main/java/ua/lpnu/kzp/Main.java` — точка входу, розбір аргументів CLI (`--help`, `--version`, `--input`, `--output`), координація читання, валідації, обчислення та запису звіту.
* `src/main/java/ua/lpnu/kzp/CsvReader.java` — зчитування рядків CSV-файлу у `UTF-8` через `Path` та `Files.readAllLines`.
* `src/main/java/ua/lpnu/kzp/DataValidator.java` — перевірка структури рядка (5 полів), непорожніх текстових полів, числових обмежень (`average >= 0`, `course > 0`) і булевого поля (`true`/`false`), повернення `ValidationResult`.
* `src/main/java/ua/lpnu/kzp/StudentReportService.java` — обчислення 4 показників (`StudentMetrics`), форматування єдиного тексту звіту (`Locale.ROOT`, `%n`) і запис у файл `UTF-8`.
* `src/main/java/ua/lpnu/kzp/BuildInfo.java` та `src/main/resources/version.properties` — читання версії з `pom.xml` та номера збірки для режиму `--version`.
* `src/test/java/ua/lpnu/kzp/` — модульні та інтеграційні тести (`CsvReaderTest`, `DataValidatorTest`, `StudentReportServiceTest`, `MainTest`).
* `data/input.csv` — вхідний набір даних варіанта 6 (4 коректні та 2 хибні записи з українськими символами).

**Потік даних:** `data/input.csv` -> `CsvReader.readLines` -> `DataValidator.validateAll` -> `StudentReportService.calculate` -> `StudentReportService.formatReport` -> консоль + `out/report.txt`.

## 5. Інфраструктура
* **Система збирання:** Apache Maven (конфігурація у `pom.xml`, Java 21, кодування `UTF-8`) із Maven Wrapper (`mvnw`, `mvnw.cmd`) для відтворюваної збірки без попередньо встановленого Maven.
* **Тестування:** JUnit Jupiter `5.12.2` (`maven-surefire-plugin 3.5.2`).
* **Статичний аналіз:** `spotbugs-maven-plugin 4.9.7.0`, прив'язаний до фази `verify`.
* **Пакування та версіонування:** `maven-shade-plugin 3.6.0` (фаза `package`) створює виконуваний `target/lab01-1.0.0.jar` із `Main-Class: ua.lpnu.kzp.Main`. Фільтрування ресурсів підставляє `${project.version}` (`1.0.0`) і `${build.number}` (`local` локально або `${{ github.run_number }}` у CI, наприклад `1.0.0+5`).
* **CI/CD та артефакти:** `.github/workflows/ci.yml` запускає `verify package` і перевірку JAR на `ubuntu-latest`, `windows-latest`, `macos-latest` та публікує артефакти `jar-ubuntu-latest-5`, `jar-windows-latest-5`, `jar-macos-latest-5`.
* **Git-тег релізу:** `v1.0.0`.
* **Посилання на запуск CI та артефакти:** https://github.com/S1nori/CPPT_Hnoianko_MI_KI-303_1/actions/runs/45018258931

## 11. Відповіді на контрольні питання
1. **Призначення `pom.xml`:** описує координати Maven-проєкту (`groupId`, `artifactId`, `version`), версію Java, кодування, залежності (JUnit 5) та плагіни життєвого циклу збірки (компіляція, тести, SpotBugs, пакування JAR).
2. **Різниця між фазами `test`, `verify` і `package`:** `test` компілює код і запускає модульні тести; `verify` додатково виконує перевірки якості (статичний аналізатор SpotBugs); `package` після перевірок пакує скомпільований код у дистрибутивний артефакт (`lab01-1.0.0.jar`).
3. **Навіщо потрібен Maven Wrapper:** фіксує конкретну версію Maven у репозиторії (`mvnw`, `mvnw.cmd`), забезпечуючи однакову відтворювану збірку на будь-якій машині та в CI без попереднього ручного встановлення Maven.
4. **Роль методу `main`:** це стандартна точка входу JVM, з якої починається виконання програми та куди передаються аргументи командного рядка `String[] args`.
5. **Відмінність примітивного типу від `String`:** примітивні типи (`int`, `double`, `boolean`) зберігають безпосереднє значення в пам'яті та не мають методів; `String` є посилальним незмінним (immutable) об'єктом класу, що зберігає послідовність символів і надає методи для їх обробки.
6. **Чому середнє обчислюють у `double`:** ділення двох цілих чисел у Java виконується як цілочислове з відкиданням дробової частини; приведення до `double` зберігає точність дробового результату.
7. **Що станеться при `Integer.parseInt("abc")`:** метод викине неперевірюваний виняток `NumberFormatException`.
8. **Чому не можна мовчки пропускати рядок із помилкою:** користувач не дізнається про втрату частини даних або причину дефекту у вхідному файлі; фіксація номера рядка та причини робить обробку прозорою та придатною для налагодження.
9. **Як `String.split(";", -1)` обробляє порожнє останнє поле:** від'ємний другий параметр `limit = -1` забороняє відкидати порожні рядки наприкінці масиву, тому рядок `"a;b;c;d;"` дасть масив із 5 елементів, де останній дорівнює `""`.
10. **Чому для шляхів краще `Path.of`:** `Path.of("data", "input.csv")` автоматично використовує роздільник каталогів поточної ОС (`\` у Windows, `/` у Linux та macOS), забезпечуючи кросплатформність.
11. **Навіщо явно задавати `StandardCharsets.UTF_8`:** гарантує однакове читання та запис кирилиці на всіх ОС незалежно від системної локалі за замовчуванням.
12. **Чим `%n` відрізняється від `\n`:** `\n` завжди вставляє символ LF (`0x0A`), тоді як `%n` у `printf`/`String.format` підставляє системний роздільник рядка (`\r\n` у Windows і `\n` у Unix-системах).
13. **Які дані потрібно перевірити у варіанті 6:** непорожність рядка, наявність рівно 5 полів, непорожні `group` та `name`, коректний формат і невід'ємність `average` (`>= 0`), додатність `course` (`> 0`) та точне значення `true`/`false` для `scholarship`.
14. **Які тести виявлять помилку в обчисленні середнього:** тест на кількох записах із дробовим результатом (перевіряє відсутність цілочислового ділення та точність до `0.0001`) і тест на порожньому списку коректних записів (перевіряє відсутність ділення на нуль / `NaN`).
15. **Призначення статичного аналізатора:** SpotBugs аналізує скомпільований байт-код без запуску програми та виявляє потенційні дефекти (помилки роботи з ресурсами, можливі `NullPointerException`, розкриття внутрішнього стану тощо).
16. **Роль GitHub Actions:** автоматично виконує збірку, тести, статичний аналіз і пакування програми на матриці операційних систем (`ubuntu-latest`, `windows-latest`, `macos-latest`) при кожному `push` або `pull_request`.
17. **Відмінність версії програми від номера збірки СІ та роль знака `+`:** версія за SemVer (`1.0.0`) відображає стан функціональності коду в `pom.xml`, а номер збірки (`42`) ідентифікує конкретний запуск CI. За специфікацією SemVer 2.0.0 знак `+` відокремлює метадані збірки, не змінюючи пріоритет самої версії релізу.
18. **Що має містити GitHub Issue на дефект:** заголовок, опис проблеми, точні кроки відтворення, очікуваний результат і фактичний результат.
19. **Що вказується у розділі про академічну доброчесність:** перелік використаних інструментів ШІ (або підтвердження їх невикористання), ролі й запити, власний внесок автора, опис редакційного процесу перевірки рекомендацій, джерела та підтвердження розуміння поданого коду.
20. **Робота агента DevOps та агента Валідатор:** *DevOps* відповідає за налаштування інфраструктури збірки, аналізатора, пакування JAR та CI/CD; *Валідатор* формує крайові випадки для тестування, перевіряє коректність обчислень і документує знайдені дефекти.
21. **Найскладніший рядок програми:** `String[] fields = line.split(DELIMITER, -1);` у `DataValidator.java`, оскільки стандартний виклик `split(";")` без другого аргументу відкидає порожні завершальні підрядки, через що рядок із порожнім останнім полем мав би меншу довжину масиву або потребував би окремої обробки.
